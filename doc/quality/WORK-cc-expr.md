# Work order: C front end, expressions, types, constants

The first of three orders for `src/frontend/c/` (with `WORK-cc-decl.md` and
`WORK-cc-cache.md`; together they own every file of `src/frontend/c/` and
`src/include/frontend/c/`, each file in exactly one).  The evidence is
`doc/review/quality-cc-expr.md` (finding ids `Q-ccexpr-NN`), with
`doc/review/quality-boundaries.md` (`Q-BND-NN`) and `doc/review/quality-lib.md`
(`Q-lib-NN`).  Names follow `doc/STYLE.md`; the "Decisions" table of
`doc/PLAN-quality.md` is binding.

Line numbers are today's (main at d602dfa2; the review's numbers still hold
for these files).  If a line has moved, find the same text.

**Starts when** WORK-common steps 1 to 3 are on main (the library's names,
`src/tools/rename-table.py`, `vjob_fail`/`vout_of_memory`).  Step 1 may run
at once; step 2 waits until WORK-diag step 2 (its renames) has merged, so
that this rename sees the engine's final names.

**Owns** (18 files, and every file they are split into)
- `src/frontend/c/`: `expr.c`, `exprop.c`, `conv.c`, `const.c`, `bitcast.c`,
  `lit.c`, `type.c`, `layout.c`, `record.c`, `complex.c`, `atomic.c`,
  `bigint.c`, `bigfloat.c`, `sym.c`, `token.c`.
- The module's three headers: `src/include/frontend/c/cc.h`,
  `src/include/frontend/c/ccint.h`, and **the shared internal header
  `src/frontend/c/ccimpl.h`**.  The other two cc orders edit `ccimpl.h` only
  (a) by script, to follow their renames, and (b) in their step 1, to add
  the prototypes of functions their moves turn from `static` into `VPRIV`,
  inside the section of the file the function came from (and, for
  WORK-cc-cache, the `builtin` declarations at `ccimpl.h:76-87` that only
  its files use).  Anything else they need there is a request to this order.
- The `cc_SRC` line of `src/Makefile`.

It edits other modules (`codegen/`, `arch/*/codegen/`, `driver/`) and the
other cc orders' files only by script, in step 2, to follow a rename.

## Rules shared by the three cc orders

- **`frontend/c/replay.c` is frozen.**  No step changes it
  (`doc/quality/MEASURE-replay.md` recommends removing it; the owner
  decides).  So a rename row whose old name occurs as a whole word in
  `replay.c` outside comments is not applied: it goes to
  `doc/quality/rename-cc-deferred.tsv`, applied when the decision is taken.
  Today that is, of this order's names: `sym_bind`, `cc_fetch`, `pragma`,
  `canon`, `fn_hash`, `ty_func`, `ty_hash`, `ty_intern`, `ty_new`, `T`, and
  the `struct cc` fields `attr cplx errors fnhash fnhcap fpool heap hp ipool
  lists ms_struct nasm nattr ndiag nfn nfpool nipool nlabel nlist nnode nodes
  npack nparams nsstack nstr nsym ntag ntk ntlasm ntoplevel nty o odir p
  pack params paren prevflags prevloc ptr_lo span sstack strs syms tags tdir
  tk toplevel ty tyhash tyhcap` (recompute at the time: the list is the
  script's output, not this paragraph).  For the same reason `ccimpl.h`
  keeps its file name (`replay.c:2` includes it): its rename to
  `cc-internal.h` waits for the decision too.
- **The `struct cc` / `ast.h` split is not in these orders.**
  `doc/quality/MEASURE-ast-split.md` has the measurement (embed `struct ast`
  first in `struct cc`); the split gets its own order later.  Hence the
  record types and enumerators of `cc.h` (`ctype`, `qty`, `node`, `sym`,
  `tag`, `field`, `N_*`, `TY_*`, `BI_*` ...), the accessor macros `N`, `T`,
  `KIND`, `ISERR`, `CT`, `CKIND`, `CN`, and the 24 `struct cc` fields code
  generation reads keep their names here: the split renames them as it
  moves them.
- **Rename steps run one at a time.**  The three orders' step 2 each touch
  callers in the others' files.  Each is generated by script on current
  main; if its PR conflicts, close it and generate it again on a new branch
  from main (no rebase, no force-push).  Moves (step 1) of the three orders
  may run in parallel: they touch disjoint files, except `ccimpl.h`
  sections as above.
- **Moves keep compiling alone.**  A `static` function that a move separates
  from its callers becomes `VPRIV` with a prototype in `ccimpl.h` (part of
  the move).  `make VCC_UNITY=` must build after every step.

## What done looks like

- One job per file in the table of step 1, each with an opening comment;
  `ccimpl.h`'s sections name the right files.
- Every file-scope function of these files is `cc_` + noun + verb, every
  global `cc_`, and the non-AST `struct cc` fields this order lists are
  words; old names are gone except the deferred rows.
- The constant evaluator is split by job, and both folders (`const.c`,
  `bitcast.c`) share the value-level arithmetic.
- Front-end lowering (complex, wide atomics, `_BitInt` casts) builds AST
  through one set of helpers in `lowering.c`.
- Output byte-identical in every step except those named.
