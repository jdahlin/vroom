# Share frozen header layers, record every read

Every compile server that shared front-end state across translation units, from Bothner's GCC server (2003) through Tromey's incremental GCC (2007-08) to zapcc (2015-18), either died of complexity or reduced itself to prefix reuse. The prefix-reuse forms are PCH, clangd preambles and modules. In each case the cause was the same: state that was mutated in place, or keyed on less than it actually read. The designs that survive in production all do three things. They treat a cached unit as a pure function of recorded inputs, as rustc's queries and Swift's lookup-instrumented dependencies do. They keep shared state immutable and index-addressed, as clang's AST files, Roslyn's green trees and Zig's InternPool do. And they check reuse by recomputation, as rustc's `verify-ich` does, which exposed 32 open unstable-fingerprint issues and forced incremental compilation off in Rust 1.52.1. The evidence supports the conclusions this conversation reached for vccd: frozen per-header layers with a per-TU overlay, keys made of recorded dependency reads (including negative ones), uncacheable when imprecise, warm output byte-identical to cold, and layers shared across threads under a memory budget. It refines four of them. A C layer must accept later *upgrades* (composite types, tentative definitions), and those belong in the overlay. Some key components are unconditional flags rather than reads. Eviction needs job-granular epochs, because today's header cache never frees. And C++ adds dependency kinds that the C cache never needed: ADL-reachable declarations, specialization generations, using-directives and constraint satisfaction. vccd owns the whole compiler, so it can do what zapcc could not: build removal and keying into the data structures instead of retrofitting them onto an AST that was never designed for either.

## Twenty years of servers died of mutation and incomplete keys

The history shows one failure in three forms: shared state that was mutated in place, global state that blocked threads, and reuse keyed on less than was read. **zapcc** kept "system" header state (AST, IR, MC, debug info and instantiations) in a clang fork. After each compile it had to *remove* the main file's state from an AST that was never built for removal. It had no invalidation of system headers: a change "will not be recognized anyhow until server restart" ([Lattner quoting Keren, cfe-dev 2015](https://lists.llvm.org/pipermail/cfe-dev/2015-May/043160.html)). It handled memory pressure by resetting the whole cache at `MaxMemory`, and C caching was disabled ([zapcc README](https://github.com/yrnkrn/zapcc)). Its claimed speedups were 2-5x on full builds and 10-50x on one-file recompiles. Lattner called the design "very complex", and zapcc stopped at its LLVM r325000 merge in February 2018. A 2025 recollection of unresolved correctness issues is anecdote only, unverified ([HN](https://hn.svelte.dev/item/45136367)). **Bothner's GCC compile server** reached "over 3x" on Apple's Carbon headers. It stayed single-threaded because GCC keeps "too much state in global variables" ([gcc 2003-02](https://gcc.gnu.org/pipermail/gcc/2003-February/099935.html)), and it ended when its author left Apple. Its reviewer had already flagged unbounded growth and asked for per-project bounds. **Tromey's incremental GCC** checksummed "hunks" of tokens between file changes and rebound their saved declarations on a match. The check that a hunk's *dependencies* had also been reused was never implemented ([Tromey, Sharing Parsed Headers](https://tromey.com/blog/?p=362)). Tromey found that conditional declarations broke reuse when include order changed, and that a file included mid-declaration needed a special case ([Hunk Boundaries](https://tromey.com/blog/?p=397)). The project was suspended, and Tromey concluded that modules address the root problem.

The coarse-key tools failed more quietly. Visual C++ `/Gm` was deprecated in VS 2019 because it "may not trigger a build for certain kinds of header file changes" ([Microsoft Learn](https://learn.microsoft.com/en-us/cpp/build/reference/gm-enable-minimal-rebuild)). Sun's template repository kept instances with old function-template signatures, and its documented remedy was `rm -rf SunWS_cache` ([Sun Studio 12 guide](https://docs.oracle.com/cd/E19205-01/819-5267/bkagr/index.html)). dmd cached speculative instantiations wrongly ([dlang 19458](https://issues.dlang.org/bugs/19458/)). distcc pump assumes headers do not change during the build, and its man page says that otherwise it can give "wrong results without warning. Presently this condition is not verified". The same page notes that the Linux build does not quite satisfy that assumption ([include_server(1)](https://manpages.debian.org/wheezy/distcc-pump/include_server.1.en.html)). Upstream clang listened to Kleckner's and Lattner's 2010 server proposal, in which Lattner said checkpointing needed immutable ASTs that clang was "close to" but did not have ([cfe-dev 2010](https://lists.llvm.org/pipermail/cfe-dev/2010-June/009480.html)), and to Gregor's "really tricky" verdict ([cfe-dev 2011](https://lists.llvm.org/pipermail/cfe-dev/2011-January/012897.html)). It converged on prefix reuse and context-free modules, not on general header-state sharing.

vccd already avoids the first two failure forms. It has job regions instead of globals, and lock-free CAS publication in the header cache, which TSan runs found clean (doc/PLAN-fas2.md, sanitizer status). Its remaining exposure is the third form, keys, and the absence of eviction.

## Keys must be recorded reads, including absences and misses

The modern systems agree on one rule: a cache entry is valid when every input it *read* still has the same answer. rustc records which queries each query reads, and marks nodes green or red by 128-bit fingerprints over session-independent identities: `DefPathHash`, never `DefId` or addresses ([rustc-dev-guide](https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation-in-detail.html)). Swift records "depends" by instrumenting name lookup. It treats under-approximation as "tantamount to a debug-time miscompile", and it has to special-case lookups that are not instrumented ([DependencyAnalysis.md](https://github.com/swiftlang/swift/blob/main/docs/DependencyAnalysis.md)). The weak point is the same everywhere: a path the hooks do not cover is a silent stale reuse. ccache documents the C version of that gap. "Headers that would be picked up if they existed, but don't yet, aren't recorded." It also refuses to cache any file whose mtime is not older than ccache's start, because a same-tick rewrite is invisible to `stat` ([ccache manual](https://ccache.dev/manual/latest.html)).

Clang's prefix and module caches show what happens when keys are *declared* rather than recorded. Clang modules make the user list `config_macros`, and warn under `-Wconfig-macros` ([Clang Modules](https://clang.llvm.org/docs/Modules.html)). C++20 BMIs check dialect options but not macros, so a `-DNDEBUG` mismatch is accepted ([StandardCPlusPlusModules](https://clang.llvm.org/docs/StandardCPlusPlusModules.html)). That is the reason for the conclusion that nothing in vccd's key is user-configured. The refinement is that a few inputs are not "reads" in any useful sense and belong in the key unconditionally. These are the language and standard, which change lexing (digit separators, `<=>`, raw strings), flags that change lexing (`-fdollars-in-identifiers`, `-fchar8_t`), and, for semantic layers, ABI-changing flags (`-fno-exceptions`, `-fno-rtti`, `-fshort-enums`, `-fcommon`, `-fgnu89-inline`). The hazard survey lists them ([ccache manual](https://ccache.dev/manual/latest.html) for the flag classes it cannot model). vccd's existing "flag signature" in the header-cache key is the right home for them.

vccd's preprocessor cache already implements this rule, and does so more precisely than any tool in the notes. Its read set covers macro value or bare definedness at entry, include guards, `#pragma once` membership, `__COUNTER__` pastes, `__INCLUDE_LEVEL__` and the search-path prefix signature. It refuses diagnostics, `#line`, `push/pop_macro` and the time macros, and the `-E` text and depfiles stay byte-identical to `VPP_NOHC=1` (doc/PLAN-fas2.md, Status 2.4). Three hazards from the survey are worth confirming against it. First, negative include lookups and `__has_include` misses must be recorded per probed directory, and directory changes during the build must invalidate them: kbuild generates headers mid-build, which is distcc pump's failure. Second, `#include_next` makes the key (file, search-directory index), not file alone. Third, a file modified within the filesystem's timestamp granularity of "now" should be uncacheable, which is ccache's rule. Keying on content hash, not mtime, removes most of that risk.

The C declaration cache in `src/driver/declaration-cache.cpp` is weaker in kind. Its trie is keyed on (header-cache entry, `__COUNTER__` at start). That key is exact only because it demands an identical *prefix* of top-level regions, the condition PCH and zapcc impose. It reaches 834 of 879 TUs but skips only 16 % of tokens (doc/PLAN-fas2.md). Its planned successor, "Declarations per header-cache entry" (doc/PLAN-fas2.md, Plan 2.13 item 2), applies the recorded-reads rule to declarations. It saves the entry's delta and its dependency answers (lookups outside the region, negative ones included), and replays the delta at a declaration boundary when the answers match. That is Tromey's hunk design with the dependency check he never built. It is also what doc/PLAN-cxx-parse.md names as cache point 2 ("key: the above + the `declared_names` lookups it made"). The conclusion to validate it on C first holds, and so does the plan's gate of building only if at least 60 % of tokens fall in entries at declaration boundaries. C is where the delta and dependency machinery can be proven against `VCC_NODC=1` before C++ adds harder lookups.

## C and C++ each break "frozen" in their own way

The conclusion that layers are immutable and every per-TU effect goes into an overlay, with no undo, is right, and the evidence for it is strong. Clang's most bug-prone machinery is the *merging* of declarations from independently built units. That machinery needed an ODR hash to stay honest, and it still has false positives and negatives ([PCHInternals](https://clang.llvm.org/docs/PCHInternals.html); ODR hash behaviour [unverified in the notes](https://github.com/llvm/llvm-project/blob/main/clang/lib/AST/ODRHash.cpp)). zapcc's removal of user state is the counterexample. Roslyn's immutable, width-based green trees are the positive model: relative positions let one node serve many contexts ([Lippert](https://ericlippert.com/2012/06/08/red-green-trees/)). vccd's snapshots already store locations relative to a base and pointers as offsets.

What the two languages add is that a *later* TU-local declaration legitimately changes a *layer* entity. **In C**, `extern int a[];` in a header completed by `int a[10];` changes the type for the rest of the TU (C11 6.2.7). So does a K&R `int f();` that gains a prototype. `int x;` stays a tentative definition until the end of the TU (C11 6.9.2), and an open `#pragma pack` or `GCC visibility push` changes the next header's layout and linkage. The overlay must therefore hold *changes to older entries*, as Plan 2.13's delta already says ("changes to older ones"). Layer-derived facts computed before an upgrade, such as `sizeof a` or call checking, must not be cached in the layer. **In C++**, clang declares special members lazily. Whether one is deleted, trivial or constexpr depends on completeness at first lookup ([class.copy.ctor], [class.dtor]). Default arguments can be added by later redeclarations ([dcl.fct.default]/4). Overload sets grow with later headers. Explicit and partial specializations may legally appear after the primary template ([temp.expl.spec]/7, [temp.class.spec]/1). The refinement is a second category besides "overlay". A lazy computation that is a pure function of the layer alone, such as the implicit members of a class whose members and bases are all complete in that layer, may be memoized *into* the layer under single-flight. Anything that also read the TU's own declarations goes into the overlay. That split has to be decided per lazy table in the C++ front end, not discovered later.

Some state must never be shared at all. Internal-linkage entities and anonymous namespaces in headers are distinct per TU ([basic.def.odr]/13 allows only the non-odr-used const exception). `__FILE__`, `__LINE__`, `__COUNTER__` and `_Pragma` results must be re-derived at replay, which the token cache already does for the counter. Friend-injected state is also out. The "constexpr counter" depends on instantiation order, and CWG agreed in 2015 that it "should be ill-formed", but the issue is still open, so a compiler matching clang must preserve order ([CWG 2118](https://cplusplus.github.io/CWG/issues/2118.html)). A file-scope `using namespace` changes unqualified lookup for every later header ([namespace.udir]), so the set of active using-directives is part of a C++ layer's entry dependencies.

## C++ instantiation caching is licensed only for programs that are already correct

The standard anticipates cross-TU reuse. A specialization "may have points of instantiation in multiple translation units", and differing meanings make the program "ill-formed, no diagnostic required" ([temp.point]/7). [temp.constr.atomic]/3 says the same for constraint satisfaction, as do [temp.expl.spec]/7 for late explicit specializations and [basic.def.odr]/13 for same tokens with the same bindings. All four clauses are NDR. A cache that returns the first TU's answer is therefore conforming, but it gives output that differs from clang's on real code that violates the ODR, which is common. A `const std::string` in a header used from an inline function is one example. Clang already caches satisfaction within a TU, which is why "satisfaction changes after a new overload" sticks to the first answer there. A cross-TU cache widens that window. The C++ counterpart of recorded reads is therefore richer than the C one. An instantiation's key is the template, its arguments, a generation counter for the specializations visible for that template, the declarations that dependent unqualified calls reached through ADL at the point of instantiation ([temp.dep.candidate], [basic.lookup.argdep]), and the flags that change instantiation (`-std` for `noexcept` in the type system, `-fsized-deallocation`, `-fchar8_t`, `-fclang-abi-compat`). zapcc avoided computing such a key by requiring the TU's preceding headers to match ([README](https://github.com/yrnkrn/zapcc), its prefix rule [unverified in the notes]). That is the fallback here as well: reuse inside an identical prefix first, and recorded-dependency reuse once its hooks are proven.

The verification side is where vccd can improve on clang. On a hit in a TU whose prefix differs, vccd can re-instantiate in a sampled verify mode and compare an ODR-style hash. A mismatch becomes a *diagnostic*, which turns NDR into an error the way clang modules do for merged definitions. doc/RESEARCH-cplusplus.md section 3.1 proposes the same check. That doc puts the cost of what this saves at about 1 KiB of AST per class template instantiation in clang, by an author's rough estimate ([LLVM Discourse](https://discourse.llvm.org/t/factoid-each-class-template-instantiation-costs-1kib/86189)). Output order is the other C++ trap. Clang emits implicit instantiations in first-use order, so COMDAT order, `.debug_info` DIE order and symbol order all follow it. A cache that hands out finished instantiations changes "first use". Byte parity with clang therefore needs the per-TU use order recorded and replayed. Lambda numbers stay per context, as the Itanium ABI requires (ABI 5.1.8, [unverified in the notes](https://itanium-cxx-abi.github.io/cxx-abi/abi.html#closure-types)), never per server.

## Memory and concurrency: index-addressed layers, single-flight, epochs

The production compilers converge on 32-bit ids into typed arrays, hash-consing so that equality is an id compare, and bulk-freed arenas. Carbon's `ValueStore`/`CanonicalValueStore` follow this pattern ([Carbon idioms](https://github.com/carbon-language/carbon-lang/blob/trunk/toolchain/docs/idioms.md)), as do rustc's interned arena types ([rustc-dev-guide](https://rustc-dev-guide.rust-lang.org/memory.html)). Zig's InternPool goes further. It is sharded by hash, with per-thread local lists, so threads intern without a global lock ([InternPool.zig mirror](https://git.medv.io/zig/blob/master/src/InternPool.zig.html)). Clang's lazy, id-based deserialization reads 0.02 % of declarations for a Cocoa.h hello world ([PCHInternals](https://clang.llvm.org/docs/PCHInternals.html)), which is the case for lazy resolution of layer entries rather than eager copying. doc/PLAN-cxx-parse.md already requires index storage and tokens by index. GCC's and MSVC's memory-image PCH show the opposite design: binary-identical requirements, and intermittent address-range failures under ASLR ([GCC PCH](https://gcc.gnu.org/onlinedocs/gcc/Precompiled-Headers.html), [MS C3859](https://learn.microsoft.com/sl-si/cpp/error-messages/compiler-errors-2/compiler-error-c3859?view=msvc-170)). vccd keeps its state live in its own address space and avoids that. If layers are ever persisted, they must be offset-encoded and keyed by the vcc binary's hash.

On concurrency, rustc's parallel front end uses single-flight. A missing key is marked in progress, other requesters block, and a dedicated thread detects deadlocks. It gains up to 50 % at 8 threads and uses up to 35 % more memory, with contention past about 4 threads, and it treats any output difference by thread count as a bug ([parallel rustc](https://blog.rust-lang.org/2023/11/09/parallel-rustc/), [dev guide](https://rustc-dev-guide.rust-lang.org/parallel-rustc.html)). Buck2 abandoned fine-grained locks for a key-to-shared-future map, and warns that locks hidden inside values are untracked data flow ([Modern DICE](https://buck2.build/docs/insights_and_knowledge/modern_dice/)). vccd's own numbers show the cost of skipping single-flight. At `-j 6` it executes 11 % more instructions than at `-j 1`, partly from "more misses in the header cache when threads record the same header at the same time" (doc/PLAN-fas2.md, vpp --batch profile). A worker that waits on another worker's key should run other `vtask` jobs rather than sleep. Ids that threads assign in arbitrary order must never decide emission order; vccd already met this as the macho qsort race.

Eviction is the gap. The header cache is "published lock-free ... and never freed", with an 8 GB cap. The declaration cache caps at 256 MB, and going to 1 GB saved only 2 % of instructions (doc/PLAN-fas2.md). zapcc's full reset and Gradle's restart-the-daemon remedy ([Gradle forum](https://discuss.gradle.org/t/how-to-force-daemons-deletion/37089.md)) are backstops, not policies. The pattern the notes support is job-granular epoch reclamation. Each layer belongs to a generation stamped with its input hashes. An invalidated or evicted layer is unlinked at once, and its region is freed when the last job that started before the unlink finishes. This needs no per-object reference counts, and LRU over whole layers keeps it within the byte budget. Long-lived data stays out of malloc, because mixed lifetimes in one heap are where daemon fragmentation comes from ([glandium](https://glandium.org/blog/wp-trackback.php?p=3723)).

## Invariants vccd should hold

| # | Invariant | Where it bites today |
|---|---|---|
| I1 | A published layer (token entry, declaration delta, instantiation) is immutable. Readers take no lock, and publication is a release store after single-flight. | header cache (holds), declaration-cache trie (holds), future C++ lazy tables |
| I2 | Every per-TU effect on a layer entity (C composite type, tentative definition, added default argument, late specialization) lives in the TU overlay. Layer-derived facts computed under such an effect stay in the overlay. | Plan 2.13 delta's "changes to older entries" |
| I3 | A layer's validity is exactly its recorded reads: macro value, definedness or absence, include lookups and misses per directory, `__has_include`, guard and `#pragma once` state, declaration lookups and misses, using-directives, pragma entry state, and for C++ the ADL-reachable sets and specialization generations. A read that cannot be recorded makes the entry uncacheable. | Plan 2.13; PLAN-cxx-parse cache points 2-3 |
| I4 | Unconditional key components are language, standard, lexing flags and ABI flags, which come from the driver's flag signature. Nothing in the key is user-declared, and there are no `config_macros`. | header-cache flag signature |
| I5 | File identity is (dev, inode) plus content hash, and `#include_next` keys on the search-directory index. A file modified within timestamp granularity of now is uncacheable. | "file rewritten within a build" in vccd-test |
| I6 | No internal-linkage entity, anonymous namespace, `__FILE__`/`__LINE__`/`__COUNTER__`-derived value, friend-injected state or non-inline lambda number crosses TUs except by re-derivation at replay. | token replay (counter holds) |
| I7 | Output (objects, depfiles, stderr) is a function of the TU's inputs only: warm equals cold, `-j1` equals `-jN`, and any job order gives the same bytes. Emission order follows recorded per-TU first-use order, never ids or cache-fill order. | `VCC_DIAG_DEDUP` stays opt-in |
| I8 | Memory is bounded: layers are freed by job-epoch reclamation under LRU and a byte budget. A full reset is a backstop, not the policy. | header cache never frees today |
| I9 | Server identity includes the vcc binary's hash, so a rebuilt vcc never talks to an old vccd. | vccd start-up |

## Conclusion

The prior art changes where vccd should spend effort. The hard problem was never the speed of replay. vccd's token replay already runs at memory bandwidth and is exact. The hard problems are completeness of the read set and the ability to throw state away, and every dead server failed on one of those two. That makes the hooks the product. Each lookup path in the C and C++ front ends either records its answer or marks the region uncacheable, and an always-available verify mode, not code review, proves that coverage. For C++ the order of work follows from the evidence. The per-header token layer carries over unchanged. Declaration deltas should be proven on C under Plan 2.13's 60 % gate before C++ relies on them. The instantiation cache should start as reuse within an identical prefix, and graduate to dependency-keyed reuse only when the verify mode turns would-be NDR mismatches into diagnostics. That last step is something no shipped compiler offers, and vccd is in a position to offer it because it owns every hook.

## Open questions

Does Plan 2.13's measurement reach 60 % of tokens at declaration boundaries? If not, should C keep the prefix trie and C++ start from the same prefix rule? How large is a C++ layer's dependency set in practice (ADL sets, specialization generations), and does checking it cost less than re-instantiating? The notes contain no numbers. Should diagnostics become replayable layer output, since they currently make a region uncacheable, or stay a reason to miss? How should vccd reproduce clang's first-use emission order when instantiations come from the cache: record it per TU, or accept a deterministic sort and give up byte parity with clang for C++ objects? Finally, what are the actual zapcc keying and DoNotZap semantics? The notes could not read `zapccs.config` or the source, and the GCC Summit papers of Bothner and Tromey were not retrieved. Their reuse criteria are therefore known only second-hand.
